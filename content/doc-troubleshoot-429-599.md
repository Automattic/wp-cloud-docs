# Troubleshoot HTTP 429 and 599 errors

A visitor-facing HTTP 429 response can represent request rate limiting or a WP
Cloud resource-limit event recorded as an HTTP 599. Check the site's logs and
metrics before choosing a fix. The page shown to a visitor does not distinguish
the two cases.

First identify the recorded status, then collect request data and reduce the
immediate impact. Use the same logs and metrics to confirm whether each change
restored legitimate traffic.

## Distinguish HTTP 429 from HTTP 599

A true HTTP 429 is shown to the visitor and recorded as a 429 in web server logs
and Metrics. It means a browser, user agent, function, URI pattern, or other
request signature is making requests that match a rate limit.

An HTTP 599 is WP Cloud's record of a request limited because the site or its
server pool could not make a PHP connection available in time. The visitor
still sees a 429 page. Look for the 599 in web server logs or Metrics rather
than assuming every visible 429 is ordinary request rate limiting.

Both statuses can appear during the same incident. Record the exact time, URL,
request method, response body or screenshot, response size, and which requests
or visitors were affected before you begin changing the site.

## Collect diagnostic data

1. Narrow the incident to a timestamp range and affected URLs. Include the time
   zone.
2. Request web server logs for that period and filter for status `429` and
   `599`. Authorized partners can use the [Get Web Server Logs
   endpoint](https://wp.cloud/docs/api/#tag/logs/POST/site-logs/{site}).
3. Compare the log results with [Metrics](/docs/monitoring-logs/metrics/)
   for the same period. Current operational charts are also available in the
   [WP Cloud host portal](https://hosts.automattic.com/wpcloud). For API access,
   use the [Time Series Metrics
   endpoint](https://wp.cloud/docs/api/#tag/metrics/POST/metrics/{type}/{key}).
   Check request volume, cache ratios, response time, PHP and MySQL CPU, PHP
   workers, `admin-ajax.php` activity, and the recorded HTTP statuses.
4. Group requests by URL, user agent, source, and request type. Include
   `page_renderer` or other renderer dimensions when they are present.
   Determine whether legitimate traffic, bots, missing assets, uncached PHP
   requests, or one slow operation dominates the incident.

An HTTP 429 can also be generated by WordPress code, a security plugin, or
another application layer. Compare the response body and headers with the log
and Metrics records before treating it as a WP Cloud rate limit. Some responses
handled entirely at the edge do not appear in origin web server logs, so an
absent origin-log entry does not by itself prove that another provider returned
the response.

Log responses can contain IP addresses, request URLs, referrers, and user-agent
values. Redact them before sharing logs with anyone who does not need access to
investigate the incident.

## Investigate a recorded 429

Some 429 traffic is normal when crawlers, scanners, or abusive clients make too
many requests, and it usually needs no action. Investigate further when a 429
blocks a legitimate operation such as an uptime monitor, SEO tool, search
crawl, API client, or customer workflow. Record the affected requests and their
impact before asking WP Cloud Support to review a rate limit.

Check for:

- One user agent, IP address, URI pattern, or request fingerprint producing a
  high request rate.
- A monitoring or search tool configured with an aggressive crawl interval.
- A sudden increase in bot traffic or a possible distributed denial-of-service
  attack.
- Repeated requests for missing pages or static assets.
- A legitimate application loop that retries without delay.

Reduce an authorized client's request rate or correct its retry behavior before
requesting a rate-limit change. If the traffic is unwanted, preserve a sample
of the requests and follow the partner's abuse or DDoS response process.

## Check for expensive 404 responses

High-traffic sites can produce 429s or 599s when visitors and bots repeatedly
request missing pages or assets. A normal WordPress 404 response can require a
full, uncached WordPress load, including for a missing static asset.

Use logs to identify the most frequently requested missing URLs. Correct stale
links, restore required assets, or add an appropriate redirect. For missing
static files, see [Static files and lightweight 404s](/docs/performance/lightweight-404s-static-files/).
Verify that the corrected request no longer produces a 404 and that the volume
of PHP-generated 404 responses falls.

## Investigate a recorded 599

A 599 points to exhausted PHP connections or other resource limits, not one
specific plugin or request. If a connection does not become available within
the platform's waiting period, WP Cloud records a 599 and returns a 429 page to
the visitor.

Common contributors include:

- Too many uncached requests reaching WordPress.
- Repeated or slow `admin-ajax.php` and `wc-ajax` requests.
- Slow database queries or high MySQL CPU use.
- Slow PHP code, plugins, themes, or external HTTP requests.
- Long page-generation times that keep PHP connections occupied.
- Organic traffic or attack traffic reaching a site that already has a
  performance bottleneck.

Do not rely on a universal PHP connection number. Allocations and available
burst capacity can differ by partner, site configuration, server pool, and
current pool conditions.

## Review rate-limit and PHP metrics

Use the current [Time Series Metrics
endpoint](https://wp.cloud/docs/api/#tag/metrics/POST/metrics/{type}/{key}) or
the host portal to compare the incident with the site's normal traffic. Useful
rate-limit dimensions include `is_rate_limited` and `rate_limit_reason`. Group
them by dimensions such as `path`, `http_user_agent`, `http_status`, or
`wp_admin_ajax_action` to find the affected requests.

For 599s, review `php_cpu_time`, `php_workers_average`, `php_workers_max`,
`php_request_limited_percentage`, `php_request_burst_percentage`, and
`php_request_normal_percentage`. Compare them with request volume and average
response time for the same period. These measurements help distinguish a short
traffic spike from PHP work that remains slow throughout the incident.

## Reduce resource use and request load

Choose changes that address what the logs and metrics show:

- Increase the share of eligible traffic served by Page Cache and Edge Cache.
  If eligible public responses continue to miss or bypass either layer, use
  [Troubleshoot Page and Edge
  Cache](/docs/troubleshooting/page-edge-cache/) to inspect the request and
  response. Avoid repeated full-cache purges while the site is under load
  because they send more requests to the origin.
- Find and optimize slow PHP functions and database queries. [Troubleshoot site
  performance](/docs/troubleshooting/site-performance/) covers a general
  investigation using [Metrics](/docs/monitoring-logs/metrics/),
  [application performance
  monitoring](/docs/monitoring-logs/apm/), [Debug
  Bar](https://wordpress.org/plugins/debug-bar/), [Query
  Monitor](https://wordpress.org/plugins/query-monitor/), and WP-CLI profiling
  packages. This article keeps the focus on the 429 or 599 incident.
- Reduce or replace excessive logged-out `admin-ajax.php` requests and
  WooCommerce cart-fragment traffic.
- Fix high-volume 404s and other routes that trigger unnecessary full
  WordPress loads.
- Review slow external requests and add safe timeouts, caching, or failure
  handling in the code that makes them.
- Avoid proxying WP Cloud domains through third-party services whenever
  possible. A proxy can obscure request signals used by WP Cloud's traffic
  protections. If Cloudflare proxying is necessary, follow the [recommended
  Cloudflare configuration](/docs/sites/domains/cloudflare/) before changing DNS or
  removing protection during an incident.

Deactivate a plugin or change production configuration only when the logs,
metrics, or profiling results point to that component and you have a rollback
plan. Test the change on a staging site when the incident does not require
immediate mitigation.

## Verify recovery

After applying a change:

1. Repeat a safe request to the affected URL from the same type of client.
2. Check the next log and metrics window for 429s, 599s, rate-limit dimensions,
   PHP CPU time, PHP worker use, and the percentage of limited PHP requests.
3. Confirm that legitimate requests complete and that page-generation time,
   query time, or PHP connection use improved.
4. Watch long enough to cover the traffic pattern that caused the incident.
   A quiet minute does not prove that a periodic crawl or traffic spike is
   resolved.
